# Beta track research report (2026-11-21): Insignia check, online Phase 1 design, Unlimited pop-in

Research only. Nothing was built or run for this report; web facts carry their source link, everything about our own code is from files in this repo. It extends docs\FEATURE_ONLINE.md (2026-11-19). Decisions wanted from the maintainer are in section 4.

## 1. Insignia check (does it support STE, what does a client need)
**Does it support the game?** Yes, as far as the public list shows: the Insignia games page lists *Godzilla: Save the Earth*, serial `IG-115 49470073`, with no extra features noted ([insignia.live/games](https://insignia.live/games), 216 titles listed when read). `49470073` is this game's title id (the same id our save paths use, `TDATA\49470073`). The listing means the title can sign on; it does not say whether the in-game Xbox Live screens work well (our scripts have both an "Xbox Live" path and a System Link path, FEATURE_ONLINE.md section 1). Community posts say it works online ([Toho Kingdom thread](https://www.tohokingdom.com/forum/viewtopic.php?t=34648), anecdotal). The service is unofficial, free, and registration needs an e-mail ([Wikipedia: Insignia (Xbox)](https://en.wikipedia.org/wiki/Insignia_(Xbox))).
**What a client needs (as documented):**
1. The title's own Xbox Live code (our recompiled XONLINES/XNET) talking through a **network card**. xemu does exactly this: it emulates the NVIDIA nForce NIC and offers three backends, NAT (a full TCP/IP stack inside the emulator routes to the internet), UDP tunnel (frames wrapped in UDP to another xemu or a real Xbox) and bridged adapter ([xemu docs: networking](https://xemu.app/docs/networking/)).
2. **DNS pointed at Insignia** (primary 46.101.64.175 in the unofficial guide, [Insignia guidebook](https://insignia-1.gitbook.io/unofficial-guide/custom-dashboard-support/pihole-dns-configuration)); a fork of xemu writes it into the EEPROM/config sector (reported by one auto-generated page, unverified).
3. **A registered console identity.** The Setup Assistant (an Xbox program) registers the console with Insignia; "your serial number is already taken" errors suggest the serial is the key ([Insignia setup-assistant releases](https://github.com/insignia-live/setup-assistant-release/releases), [ConsoleMods wiki](https://consolemods.org/wiki/Xbox:Online_Play)). On a real Xbox or in xemu the serial and keys live in the EEPROM (256 bytes).
**What this means for us.**
- Our recomp has no EEPROM and cannot run the Setup Assistant (it is a different XBE; we only run the game's code). To sign on we would need a **console identity**: serial, MAC and the keys the XDK crypto reads (HDD key, signature/online keys through kernel exports). **We will not use anyone else's keys.** The only clean sources are (a) values we generate randomly per install, or (b) the player's *own* EEPROM file from their own xemu profile or console, read locally and never shipped. Whether Insignia accepts a registration done in xemu being presented by a different client (our recomp) is unknown and is for the Insignia team to say: **we should ask them before building anything against their servers** (a new kind of client, traffic volume, and they may need to whitelist or object).
- Network layer: Insignia is reached through a **NAT-style backend** (the game's DHCP/DNS/TCP/UDP go out through a gateway we emulate), not through our two-PC frame tunnel. A NAT backend means a DHCP server, DNS forwarder and UDP/TCP translation inside our process: either our own small stack or an embedded **libslirp** (BSD-3-Clause, from QEMU; would be credited in CREDITS.md part 1).
- Unknown until tested: whether the 5849 XDK's XOnline logon needs kernel crypto/data exports we currently stub (`XcSHA/HMAC/RC4`, `XboxHDKey`, `XboxSignatureKey`, `XboxLANKey`, `XboxHardwareInfo`, EEPROM `ExQueryNonVolatileSetting` indexes), and the clock (logon tickets are time-checked). Our kernel bridge logs show unhandled non-volatile setting indexes 0x103/0x104 today.
**Verdict:** supported as a title; connecting like xemu is possible in principle (NIC + NAT/slirp + own generated or player-owned identity), but it is **Phase 2.2 after Phase 1**, with an XL unknown (identity, crypto exports, Insignia's blessing). Phase 1 delivers the NIC that Insignia would need anyway.

## 2. Online Phase 1 design: network card emulation + secure UDP tunnel for System Link
Goal: two PCs play the game's **System Link** (LAN) mode with no change to game code (no XDK overrides, STOP-class rule respected).
**2.1 NIC emulation ("nvnet").** The game's XNET library (77 KB in `default.xbe`) drives the NIC through MMIO at `0xFEF00000` (register file, MII/PHY access, TX/RX descriptor rings in guest RAM, interrupt). Plan: a new `xboxrecomp/src/net/` device with the same hook pattern as the APU/NV2A MMIO (`apu_mmio_hook.c`): registers (IRQ status/mask, MAC address A/B, ring physical addresses and sizes, TX/RX control, MII control/data answering a link-up PHY), descriptor processing (TX: copy frame from guest RAM, hand to backend; RX: write frame into the next free descriptor, set flags, raise the interrupt), and the kernel's link query changed from "no link" to "link up" **only when a peer is configured** (today the default avoids a 20 s DHCP stall, 0.1.4). Own implementation from the public register documentation of the nForce NIC (Linux `forcedeth` driver notes) and observation of what the game's driver touches (logging build first); xemu's `nvnet` device is behavioural reference only (GPL-compatible, but copying it would put it in CREDITS part 1; own code is cleaner). Risk: interrupt/timing details of the 2004 driver.
**2.2 Tunnel.** One UDP socket; every Ethernet frame the guest sends (and only those the guest sends: no host network access, no pcap/Npcap, no admin) goes to the peer as one AEAD-protected datagram; received datagrams are validated and delivered to the RX ring. The peer pair behaves as one Ethernet segment, so the game's own link-local addressing, broadcast advertise (`DNetLobby`) and join work unchanged. Frames up to 1514 bytes plus header and 16-byte tag exceed a 1500-byte path MTU: let the OS fragment (LAN/VPN fine), and drop-with-count anything over a configured size; game packets are small. Settings: `[online] peer`, `tunnel_port`, `invite`; launcher Online page (launcher session).
**2.3 Security (design in from day one).**
- Session secret: the host generates 256 random bits shown as an invite string (base32) together with its address; keys derived with HKDF; AEAD per datagram with a 64-bit counter nonce and a replay window; anything that fails authentication is dropped silently. No cleartext, no unauthenticated peer ever reaches the guest. Crypto: Windows CNG (AES-GCM, SHA-256, HMAC) needs no new dependency but is Windows-only; **Monocypher** (BSD-2 / CC0, one file) keeps it portable (portability rule 2026-11-06). Either way listed in CREDITS part 1.
- Frame validation before guest memory: length 60..1514, TX/RX descriptor ring bounds, DMA addresses only inside guest RAM, rate limits (frames/s, bytes/s), only Ethernet types the game uses (ARP, IPv4 UDP/ICMP), drop the rest.
- One UDP port, user-configurable; no inbound ports other than the host's forwarded one; peers see each other's IP (as in any P2P game); no accounts, no logs unless asked. The 2004 netcode parses what it receives and was never hardened: the authenticated tunnel limits who can reach it to the invited peer.
**2.4 Testing.** Needs two game processes. Our rule forbids two instances on one PC (a zombie instance locks the save images and crashes the next); that rule exists for save-lock safety and coordination, and separate `RECOMP_SAVE_DIR`s plus a loopback tunnel may make a one-PC test safe: **needs the maintainer's OK to try**. Otherwise a second PC. Unit level: replay captured/synthetic ARP/DHCP/UDP frames through validation and the descriptor code (no game needed) and fuzz the tunnel parser.
**2.5 Effort.** About 3-6 weeks as estimated in FEATURE_ONLINE.md; the logging build that shows exactly which registers the driver uses is the first week and decides the estimate. Internet play afterwards = rendezvous/hole-punch (Phase 2.1) or the NAT backend for Insignia.

## 3. Unlimited pop-in
**State of knowledge (all from earlier work in this repo).** `draw_distance=unlimited` overrides the game's per-object draw tests (`sub_0013BE90/13C0A0/13C2D0`, `sub_0017D1F0/17CDD0`; depth is forward depth, so widescreen sides popped; c242) and fog is scaled x8. The remaining skyline pop-in came from the **per-frame scene query volume** (`sub_0013DF10`, record `0x3F1150 + list*0xCC`: far bound at +0x60 and its box), refilled every frame; `query_scale` widens it at the query entry and restores it at the return (c307, default 1.5, governor `query_scale_auto`). Measured cost: x1.5 about -3 fps at 1765x993, x4 halves the frame rate (both threads CPU bound, ~1 us per draw on the game thread). The photo-mode camera confirmed the overrides are camera-relative. Open from earlier reports: "Unlimited pop-in not verified / pop-free clips not delivered" (REPORT_0.2). Also noted: the LOD pick returns mesh 0 for about 2 % of calls (empty LOD slot), and the Tokyo UFO is not a distance-cull case (it is a script object).
**What is missing is a measurement, not another override.** Proposed first step (research, logging only): (1) a repeatable pop metric: scripted camera path (the photo-mode scripted camera already exists) in Tokyo and New York, record per frame the set of draw keys (the `STE_POPLOG` census tooling) and count objects that appear or vanish while inside the screen frustum at distance d, binned by distance, for original / unlimited x1 / x1.5 / x2 / x4; (2) check where the first vanish distance sits relative to the fog end (Tokyo 1250/2100, fog x8 in unlimited): pop beyond the fog end is invisible, pop inside it is the target; (3) decide among: (A) keep x1.5 default but add **hysteresis** (an object that was in the list stays until a larger radius, so objects do not flicker at the boundary; draw-list only, no game-state change); (B) a **distance-proportional far list** instead of a uniform multiplier (widen only the far slab's tail, cheaper than x4); (C) a far-LOD fallback for the 2 % empty-slot case. All are draw-side changes, inside the existing STOP rule (they do not touch update/AI/physics), but the hook at the query entry is a game-function hook: **report-first item**.
**Effort:** measurement 3-4 days, then one of A/B/C 3-5 days with verified clips (check_clip/verify_clip, 1080p60, new-feature clips only when the launcher asks).
