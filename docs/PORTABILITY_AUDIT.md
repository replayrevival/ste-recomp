# Portability audit: Linux and macOS (goal 7)

Read-only audit, 2026-11-06. No code or build was changed. Paths are relative to `E:\GodzillaSTE`: `tools/xboxrecomp-v014k/` is `xboxrecomp/` in the publish repo, `tools/xboxrecomp-v014/templates/runtime/recomp_types.h` is the generator's runtime header, `ste-recomp/mission-l6/tmp/c262src/` holds the exe-side sources (`ste/src/` in the publish repo; line numbers there are of c262 and move slightly between candidates). "Counts" come from grep over `*.c/*.h` without `third_party`. **All effort numbers in this document are estimates** (my judgement), in person-weeks of one developer who already knows the code; nothing here was run on Linux or macOS.

## Summary
- The game is already a **64-bit** program and the generated code is **base+offset**, so the big blockers of a typical 32-bit port do not exist. Apple Silicon is possible in principle.
- The upstream runtime we forked already carries a POSIX layer (Win32 primitives, mmap-based guest memory, SIGSEGV/SIGBUS MMIO traps including an AArch64 instruction decoder, SDL2 audio, an OpenGL 3.3 D3D8 backend). **Our additions** (Kelvin to D3D11, HLSL shader generators, XAudio2, Win32 window and crash code in the exe) are Windows-only and are the work.
- The real cost is the **renderer** (about 14 k lines of D3D11 code). Recommendation: SDL3 GPU with SDL_shadercross and the existing HLSL kept as the single shader source; Proton/Wine first as a cheap Linux check.

## 1. Bitness and guest addressing
- **64-bit host.** The build runs `vcvars64` and links with no `/MACHINE:X86` (`ste/scripts/build.ps1` in the publish repo; `mission-l6/candidate261/relink261.bat` link line has only `/LARGEADDRESSAWARE`, which is a no-op on x64). Host pointers are `ptrdiff_t`/`uintptr_t` (`xbox_memory_layout.c:1690`, `kernel_bridge.c:58`).
- **Base + offset, not raw pointers.** Every guest access in generated code goes through `XBOX_PTR(addr) = (uintptr_t)(uint32_t)(addr) + g_xbox_mem_offset` (`tools/xboxrecomp-v014/templates/runtime/recomp_types.h:509`; `MEM8/16/32` and `SMEM*` follow). The offset is set once (`xbox_memory_layout.c:3027`) and is 0x10000 on this PC. The generated chunks contain no `long`, no inline asm and no intrinsics (grep over `candidate86/generated`, 19 files, 97 MB: 0 `__asm`, 0 `_mm_`, 0 `long`).
- Guest state is thread-local C variables (`g_eaxâ€¦`, `g_fp_stack`; `RECOMP_TLS` already maps to `__thread`/`_Thread_local`, `recomp_types.h:161-165`).
- **What 64-bit POSIX needs.** Nothing structural for the generated code. The loader needs the 4 GB guest window reserved with `mmap` and carved into windows (the physical/contiguous mirrors at 0x80000000 are aliases of the same RAM); upstream has this (`xbox_memory_layout.c:85-105`, `RECOMP_EXT_VMA`, `MAP_FIXED_NOREPLACE`, `guest_vmem.c`) and our Windows path uses VirtualAlloc2 placeholders (`xbox_memory_layout.c:159-186`). Open points: `MAP_FIXED_NOREPLACE` does not exist on macOS; macOS arm64 pages are 16 KB while the guest tracks 4 KB pages (`guest_vmem.c` `VMEM_PAGE 4096`) and traps device pages with page protections, so the MMIO pages need 16 KB alignment or a different trap scheme (not verified how upstream's macOS path handles this).

## 3. x86-specific code and ARM64
- **x87 is software.** The lifter models the x87 stack as `double[8]` per thread with its own control/status words, precision-control and rounding handling (`recomp_types.h:171-330`, PC=24 rounding note at :268). Nothing depends on the host FPU mode, so results do not depend on the host CPU. x87 transcendentals use libm (`sin/cos/tan/atan2/log2/exp2/fmod`, `recomp_types.h:52-60`); libm results can differ in the last bit between glibc, macOS libm and MSVC CRT. Whether the game's logic is sensitive to that is unknown; the fight simulation is delta-time driven (memory `project_gpu_vp_and_dt_timing`), so a divergence shows as drift, not as a break.
- **SSE.** `rcpss`/`rsqrtss` use `_mm_rcp_ss`/`_mm_rsqrt_ss` on x86 and a portable fallback elsewhere (`recomp_types.h:689-700`): the x86 instructions return approximations with specific bit patterns, the ARM fallback returns exact values, so SSE-based approximation idioms (Newton refinement) will give slightly different floats. Conversions use `_mm_cvt*` on x86 with a fenv fallback (`:1283-1307`). The generated code carries 12135 `XMM_*`/`__m128` tokens: those go through the runtime's lanewise macros, not intrinsics.
- **Unavoidable ISA bits.** `rdtsc` is emitted twice (`recomp_0010.c:37811`, `recomp_0011.c:42502`, as a host TSC read) and `cpuid` four times as `RECOMP_UNIMPL` (`recomp_0011.c:119564â€¦128001`). Both are harmless on ARM64 if `rdtsc` is replaced by `cntvct_el0` or a monotonic counter.
- **Compiler floating-point contraction.** MSVC `/O2` on x64 does not emit FMA unless asked; clang on ARM64 contracts `a*b+c` by default (`-ffp-contract=on`). The recompiled float code must be built with `-ffp-contract=off` (and no `-ffast-math`) to keep results equal to the x64 build. Not tested.
- **Little endian** everywhere: the guest is x86, and ARM64 Apple/Linux are little endian, so no byte swapping is needed (our Wii-format work, goal 3f, is separate).
- **Unaligned and volatile access.** Guest loads/stores are `volatile` casts of unaligned addresses (`MEM32`, `recomp_types.h:514`). ARM64 permits unaligned access to normal memory; the trapped MMIO pages need the AArch64 decoder, which upstream provides (`mmio_decode_a64.h`: LDR/STR, LDP/STP, SIMD forms; exclusive/atomic forms deliberately unsupported). Our hooks and `MEM*`-heavy hand code have not been checked for atomics on device pages.
- **LLP64 versus LP64.** `unsigned long` is 32-bit on Windows and 64-bit on Linux/macOS. Our kernel layer uses `(unsigned long)`/`DWORD_PTR`-style code heavily: 197 hits in `kernel_thunks.c`, 41 in `kernel_bridge.c`, 28 in `d3d8_device.c`, 16 in `kernel_hal.c`, 15 in `nv2a_kelvin.c`. `xbox_winnt.h` maps DWORD to `uint32_t` on POSIX, but each of these needs a review (every `%lu`/`%08lX` printf with a DWORD is also a format-warning source).
- **Apple Silicon extras (not verified):** W^X/JIT is not needed (no runtime codegen); there is no 32-bit and no low-4 GB requirement because the guest base is arbitrary; Rosetta 2 would run the x86-64 build as a stop-gap but still needs the renderer.

## 4. Renderer options
Scale of the problem: `d3d/*.c` 10.8 k lines plus `nv2a_kelvin.c` (3.2 k lines, 73 `lpVtbl` D3D8-vtable calls and 17 distinct `d3d8_*` entry points into the device layer). The Kelvin path translates NV2A state itself, generates HLSL **at run time** (vertex programs from NV2A microcode `d3d8_kvp.c`/`nv2a_kelvin.c:496-780`, register-combiner pixel shaders `d3d8_nv2a_psh.c`, fixed-function `d3d8_shaders.c`, FSR1 pass) in **Shader Model 5** (`vs_5_0`/`ps_5_0`, `d3d8_kvp.c:99,141`, `d3d8_nv2a_psh.c:456`), caches the DXBC on disk and compiles on a worker thread (`d3d8_shcache.c:92,136`). Things D3D11 gives us that other APIs do not: a geometry shader with stream output exists only in the GPU-vertex-program **verify** pass (`d3d8_kvp.c:296`, debug only, droppable); no compute shaders (0 hits), no UAVs (0), 3 blend/3 depth/3 raster state creations (the states are few), the 17 query hits are the GPU timestamp/pipeline-statistics profiler (`d3d8_device.c:1379-1384`, STE_GPUSTAT, debug only). `xbox_winnt.h:126-128` already makes `DWORD/ULONG/LONG` 32-bit types on POSIX.

**(a) SDL3 GPU (Vulkan on Linux, Metal on macOS, D3D12 on Windows) with SDL_shadercross.**
- Keep HLSL as the single shader source. Compile at run time with shadercross (DXC to SPIR-V, SPIRV-Cross to MSL/â€¦): ships `dxcompiler` and SPIRV-Cross with the game. Replace the DXBC disk cache by a SPIR-V/MSL cache.
- D3D11 immediate state becomes pipeline objects: key the pipeline cache on (shader pair, blend, depth, raster, render-target formats, topology) and build them asynchronously, or the first fight shows hitches (we already fight shader-compile stalls: `[SPIKE] new shaders` log, `d3d8_shcache.c`).
- Re-do: render-target/texture creation, dynamic vertex upload (`DrawPrimitiveUP` ring buffers, 51 `Map` calls), readback for screenshots/ring (staging), swap-chain modes (V-Sync, tearing/VRR is a present mode), the second D3D11 device plus keyed mutex (collapses into one device and a fence). FSR1 is plain HLSL/GLSL and ports as a fragment pass.
- Behavioural risks: clip-space depth range (Metal/Vulkan 0..1 as D3D11, but Y flip differs in Vulkan), texture formats (BGRA/RGBA, DXT, 16-bit), point/line primitives (the Kelvin path draws points, e.g. 15-point flash draws, prim=1), alpha-to-coverage/`discard` behaviour for the combiner shaders, MSL float precision.
- Estimate: **8-12 weeks** for Vulkan on Linux with parity on the validator/soak scenes, **+3-5 weeks** to bring up Metal (shadercross/MSL differences, 16 KB pages, notarisation test loops). Windows could stay on D3D11 in parallel at the cost of two backends, or move to SDL GPU's D3D12 later.

**(b) dxvk-native (Linux only).**
- Keeps the D3D11 code. Needs: DXGI swap chain on an SDL window (dxvk-native has an SDL2 WSI; SDL3 not verified), Windows headers (dxvk-native ships `native` headers or use mingw-w64 headers), and an `D3DCompile` replacement (dxvk-native does not provide one; vkd3d-shader's HLSL front end or Wine's `d3dcompiler_47` would be needed; SM5 coverage of our generated HLSL is unknown).
- macOS is not covered (DXVK needs Vulkan; MoltenVK works for some D3D11 titles but dxvk-native on macOS is not a supported target; not verified).
- Estimate: **3-5 weeks**, Linux only, with a risk in the shader compiler.

**(c) Other.**
- Extend the upstream `d3d8_gl.c` (OpenGL 3.3 via SDL2 + libepoxy, 43 KB) to our Kelvin pipeline: needs GLSL generators for the three HLSL generators; OpenGL is deprecated on macOS (frozen at 4.1) and has no path to Metal; not recommended.
- Wine/Proton running the Windows build: zero code, Linux only, tests whether the current D3D11 build behaves under DXVK/vkd3d. This is phase 0 below.

**Recommendation: (a).** It is the only option that covers Linux, macOS (Metal) and Windows from one renderer, uses the existing HLSL generators unchanged, and puts the pipeline-cache work in one place. Do (b) only if a Linux-only early build is wanted and the `D3DCompile` question is answered first.

## 5. Launcher
Already portable: C++ with SDL3 (static), RmlUi GL3 renderer, nlohmann json (`launcher/CMakeLists.txt`); the game process is started with `SDL_CreateProcessWithProperties` and a per-launch environment (`src/platform/GameProcess.cpp:22-60`), file dialog `SDL_ShowOpenFileDialog` and `SDL_OpenURL` (`src/ui/App.cpp:447-453`), the XISO unpacker is plain C++/`std::filesystem` (`src/core/xdvdfs.cpp`).
Windows-only or Windows-assuming: `DriveSearch.cpp:7-39` (drive letters A-Z; on POSIX scan `/media`, `/mnt`, `/Volumes`), `ExeVersion.cpp:3-22` (reads the exe's VERSIONINFO with `VerQueryValueW`; use the `--version` output instead), `xdvdfs.cpp:37` and `:151` (Windows reserved-name and character rules; keep as a safe superset), `UNICODE _UNICODE` compile definitions, the `.exe` name in `config/profile.json` (`"exe": "ste-recomp.exe"`) and `config.cpp:19`, backslash handling (`App.cpp:447`), per-user data path conventions (portable `data\` today). Distribution: AppImage/tarball on Linux; `.app` bundle, codesign and notarisation on macOS. Effort: **1-2 weeks**.

## 6. Phased plan
0. **Proton/Wine check (about 1 week, needs a Linux machine or WSLg).** Run the shipped Windows build under Proton (DXVK + vkd3d) with a copy of the game: confirms D3D11 + XAudio2 + VEH behaviour under Wine, finds missing Win32 calls, gives a Steam Deck/Linux answer immediately. No code changes expected beyond documentation; failure modes tell us how much of Windows we lean on.
1. **Native Linux x86-64 (12-18 weeks).** (1a) CMake + clang build of the 21 generated chunks and our runtime on Linux with `-ffp-contract=off` (2-3 weeks incl. LP64 clean-up and the file-path case layer); (1b) POSIX window/input/audio/crash/INI replacements in the exe and libs (2-3 weeks); (1c) renderer (a): SDL3 GPU on Vulkan (8-12 weeks); (1d) soak and validator parity runs with image comparison against the Windows build (1-2 weeks); launcher port (1-2 weeks, can overlap).
2. **Native macOS arm64 (+6-10 weeks after phase 1).** Metal through SDL3 GPU (3-5 weeks of shader/pipeline differences), 16 KB page and MMIO trap scheme plus `MAP_FIXED_NOREPLACE` replacement (1-2 weeks), AArch64 decoder gap review for our MMIO accesses, Info.plist/bundle, codesign and notarisation (needs an Apple Developer account), Apple GPU performance tuning (1-2 weeks). Rosetta 2 with the phase-1 x86-64 binary is a possible stop-gap during bring-up.
3. **Native Linux arm64** comes almost free after phase 2.

Total for a Linux release: roughly 3-4 months of focused work; macOS adds 1.5-2.5 months. The dominant risk is the renderer parity (shaders and state) and the unverified FP behaviour on ARM; both are testable early by running the validator and the soak scenes on the new backend before polishing.
