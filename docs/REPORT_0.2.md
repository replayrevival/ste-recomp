## 1a'. Instant typing DONE (c428, D1A5A6AC1DC4B87797D2A9674216EEAA8DCABC5847C8E7091F2D1021078CED71, 0.2.0+c428; patches\c428_instant_typing.patch) -- approved by Miko
- Cause/mechanism found by RAM snapshots at known cursor/keystroke states (tests\pads\kb_cursor_probe.pad.txt, STE_SNAP_T, F:\GodzillaSTE_work\kbsnap): the profile name is an ordinary NUL-terminated heap string (0xCD fill after it; max 10 characters in the game: 30 A's end as AAAAAAAAAA; allowed A-Z 0-9 space) that the keyboard screen shows every frame and that END saves. Two dead ends logged: (1) the selected-key pointer (three copies, 0x100 per key / 0xB80 per row) and (2) the two cursor column/row float arrays (script boxed values) are both mirrors: writing them did not move the highlight (c427 experiments, kb427_tp / kb427_tp2); the cursor is only changed by the script's own setCursor.
- c428 method: the first two letters are typed the old way (two A presses at the start cursor, about 0.1 s, shown as "AA"), the buffer is found by its content ("AA", NUL, 0xCD fill: exactly one place in RAM, scan of the 64 MB guest RAM about once per name entry, else the module falls back to walking for the session), then every typed letter is written into the buffer at once (max 10 characters, A-Z 0-9 space, Backspace removes the last one, Tab = END is still walked). Before each write the buffer must still hold what we last wrote, else start over. Only the name string is written. `STE_TEXT_ENTRY=walk` = the 0.2.0 walking method.
- Evidence: GODZILLA+END (kb428_c): 'AA' then GODZILLA on screen about 0.3 s after the first key; the game's own save prompt then reads "Saving GODZILLA" and "The saved game already exists GODZILLA" (an earlier test had saved that profile): the saved name is the written one. 12 letters -> ABCDEFGHIJ (10). ABCD + 2 Backspace + XY -> ABXY. Walk mode still works (GO typed by walking, fin428_walk). 420 s Tokyo fight: 0 ICALL/STUB/CRASH, median 59.4 fps. Validator PASS. Clip: release\media\0.2\clips\keyboard_typing_instant.mkv.
- Not tested with a physical keyboard (the harness feeds the same queue through STE_TE_TEST); the keyboard code path (window thread -> queue) is unchanged.

## 1c. RAGE announcer: reproduction path and first evidence (2026-11-19, c428; still no fix)
- Method that works (no new build needed): `RECOMP_APU_TRACE=1` prints one `[APU-VSTAT] t=<s> v=<voice> ... addr=<sample address> rms=` line per playing voice per second; the English announcer bank godzilla_voice_e.samp (998,212 bytes) sits linearly in guest RAM at 0x01716B40..0x0180AA84 in the Tokyo fight run (found by matching its bytes in a RAM snapshot), so a voice whose addr is in that range is an announcer line. godzilla_voice_e.uber: sections PROJ (66 12-byte records), POOL (cue entries), SDIR (64 samples: records of 4 dwords, sample k start = previous start + size + 0x14; sample 27 = 0x56A14, 17,316 bytes) and 201 alphabetical cue names (index 163 = RAGE, 171 = WINNER, 170 = TIME UP, 142 = GAME OVER); the cue-name -> sample mapping (POOL) is not decoded yet.
- Test-only rage trigger (existing STEM option, nothing added to the exe): `STE_ENHANCE_STEM_RULE_RAGE_METER=5` + `STE_STEM_LOG=1` + the scripted Tokyo Godzilla 2000 vs Gigan fight: the COM monster (slot 1) enters rage mode at audio second ~346 (STEM log inrage_frames 182 at second 349) in two runs (F:\GodzillaSTE_work\rage_b with RECOMP_APU_TRACE, clips_try\rage_a with video+WAV: Gigan's rage flash at video second ~18-21).
- Result: announcer-bank voices play in seconds 305-315 (match start) and 348-350 (rage start: one sample, #27, addresses 0x0176D684 -> 0x0177033C, rms > 0 on a voice): so a voice line from the announcer bank DOES play at a meter-triggered rage start in our build, and the audio layer starts the voice normally. It is not known whether sample 27 is the "RAGE" cue. Miko's report is about the rage POWER-UP pickup (script ConventionalGame::onPickupPowerup: Powerup_rage_grab.edf, setRageMeter, StartRageMode; no playVoice/playSound in that handler, the announcer call is inside the native StartRageMode / rage code), which is not the path tested here. Next step: force a rage power-up pickup in a scripted fight (power-up drops come from the delivery UFOs ConventionalGame::onPowerupUFOStart; the type comes from selectPowerupType* which uses rnd: try STE_RAND_SEED values until a rage drop is picked up, or a test-only write of the chosen type), run the same APU trace, and compare the voices at the pickup with sample 27; if no bank voice starts, trace StartRageMode (probe hook) for a skipped call.

## 1d. RAGE announcer: rage pickup reproduced, the line plays (2026-11-19, c428)
- Seed search (test-only, STE_RAND_SEED, off by default): seed 11 (F:\GodzillaSTE_work\seed_11, scripted Tokyo Godzilla 2000 vs Gigan, rage meter option OFF, so rage only by a power-up pickup) gave a rage pickup by the COM monster (STEM log inrage_frames slot 1 = 149 at audio second 330, i.e. rage mode from about second 327.5).
- APU trace of that run: the announcer-bank voice (always voice 69, format A000E0E6 = 16-bit PCM at 11025 Hz, vol 180/180, bins 0/1, same as every other announcer line) plays sample 27 of godzilla_voice_e.samp (17,316 bytes) at seconds 329-332, rms up to 9983: the same sample 27 that plays at the meter-triggered rage start. So in our build the audio layer starts, mixes and outputs the rage announcer sample normally (no skipped/failed bank or sample lookup, no priority or voice-allocation loss, no stub hit, same voice/volume/routing as the match-start and winner lines: samples 13, 14, 37, 11, 12, 33, 34 at 305-316 and 18, 19, 31, 12 at 426-431). Rage onset to voice start is about 1.5 s (the rage flash/cutscene in between).
- What is NOT shown: (a) that sample 27 is the cue "RAGE" (the cue name -> sample mapping lives in the .uber POOL/PROJ tables: POOL entry n holds sample index n, the 201 alphabetical names are not tied to POOL entries in a way I decoded); (b) a pickup by the HUMAN player (the scripted fights never make P1 pick up a power-up); (c) the original game's behaviour for comparison. Static trace: the rage power-up grab handler (ConventionalGame.bsf onPickupPowerup) only calls the natives setRageMeter and StartRageMode; native descriptors are resolved by name by sub_000FBE20 (startRage = id 0x73 at 0x310EBC), the handler table was not located (the 0x352c50 table is not it). No stub, ICALL FAIL or skipped call appeared in the rage runs.
- Conclusion so far: the line DOES play for AI rage pickups. Miko's report (no "RAGE" at pickup) is not reproduced; the remaining candidates are a human-player pickup, a different timing in the original (line at pickup instead of after the rage flash) or another cue (e.g. when a rage power-up appears). Needs Miko's exact scenario (who picks it up, what she hears and when) or a human-pickup test.
