# Online play design: player-hosted, password-protected, no server (2026-11-22)

Decision (maintainer): no central server, nothing for the project to run or maintain. One player hosts, up to 4 players total, protected by a password. This replaces the "relay or matchmaking" ideas in `REPORT_BETA_RESEARCH.md`. Status: **design only**. Nothing is built yet and the title does not transmit a single frame on the System Link screen so far (see "Where we are").

## 1. Plain words (summary)

- **What players see.** In the launcher: *Online > Host* (pick a password, press Start) or *Online > Join* (type the host's code and the password, press Join). Then the game starts and the player goes to Multi-player > System Link as on a real Xbox. Up to 4 players.
- **How the connection works.** The game already thinks it has an Xbox network card (our emulation). We carry what that card "sends" inside an encrypted internet connection to the other players' games. The host's game acts as the hub; the others connect to the host. There is no project server in between.
- **The code.** The host's launcher shows a short code (it contains the host's address, port and a random salt). The host shares the code and the password with friends by any chat.
- **The password.** It is never sent. Both sides derive the same secret key from it. A wrong password means the host silently ignores the joiner (no error message that could help a guesser). Repeated wrong tries from one address are slowed down and then blocked for a while.
- **Getting through the router, no server needed, three ways (in this order):**
  1. Automatic: the launcher asks the router to open one UDP port (UPnP / NAT-PMP). Works on many home routers.
  2. Manual port forwarding: one UDP port to the host PC; the launcher shows a step-by-step guide with the exact port.
  3. A VPN such as Tailscale or ZeroTier: no router changes at all; players join using the VPN address.
- **Insignia** (the community Xbox Live replacement) is optional and only if they agree. Nothing here depends on it.
- **Safety.** Off by default. Only the host listens, only while hosting. Everything arriving is checked (encryption tag, size, order) before the game sees it. Joiners only ever see the host. No game data is sent, only the network traffic the game itself produces.
- **What I need from you:** nothing now. Next steps are listed in section 6; the first one (make the game actually send frames) is research, not UI.

## 2. Architecture

```
 Joiner game ──(emulated NIC, L2 frames)──┐                      ┌── Joiner game
                                          ▼                      ▼
                          tunnel (UDP, encrypted)      tunnel (UDP, encrypted)
                                          └────────► HOST game ◄──┘
                                  (host's NIC emulation + a tiny virtual switch)
```

- The tunnel lives **inside the game executable**, next to the NIC emulation (`xboxrecomp\src\kernel\nvnet.c`), because that is where Ethernet frames appear. The launcher only configures it and shows status.
- Star topology: joiners talk to the host; the host forwards frames between its own NIC and all joiners (a virtual switch: learns source MACs, floods broadcast/unknown, sends unicast to the right peer). Joiner-to-joiner traffic goes through the host. 4 players = 1 host + 3 joiners.
- Layer 2 tunnel: one Ethernet frame per datagram. System Link discovery is broadcast-based, so the bridge must carry broadcasts.
- Default UDP port: 47474 (configurable). Not 3074, which is the console's own System Link/Live port and would be confusing on a LAN with a real console.

## 3. Cryptography (Monocypher)

Library: Monocypher (public domain / BSD-2-Clause, portable C, no dependencies; chosen for the planned Linux/macOS ports). It goes into CREDITS.md **part 1 ("Code and assets used")** in the commit that vendors it, with version, licence, hash and file list.

- **Key from password:** `crypto_argon2` (Argon2id) with a 16-byte random salt generated by the host per hosting session and carried in the code. Cost parameters chosen so a derivation takes about 0.3 s on the host machine (memory 64 MiB, 3 passes, 1 lane; tunable, recorded in the handshake version byte). Output: 32-byte `psk`.
- **Handshake (one round trip, no secret on the wire):**
  1. Joiner → host: `HELLO = version | joiner_nonce(24) | AEAD(psk, nonce=joiner_nonce, "join", timestamp)`.
  2. Host verifies the tag; on failure it sends **nothing** (no oracle) and counts the failure for that source address. On success it replies `WELCOME = host_nonce(24) | AEAD(psk, ..., slot, player count)`.
  3. Session keys: `BLAKE2b(psk, joiner_nonce | host_nonce | direction)` gives one key per direction, so a nonce can never repeat across directions.
- **Data packets:** `slot(1) | counter(8) | ciphertext | tag(16)` using `crypto_aead_lock` (XChaCha20-Poly1305). The counter is the nonce; the receiver keeps a sliding replay window and drops anything old, duplicated or with a bad tag. Frame size is validated (14..1514 bytes) after decryption, before it reaches the NIC.
- **Rate limits and abuse control (host):** at most 1 Argon2 derivation per hosting session (the psk is cached); HELLO verification is a cheap AEAD check; per-source-address limit of 5 failed HELLOs per minute, then a 10 minute block; global cap of 20 HELLO/s; at most 3 live peers; unauthenticated packets are never answered. Timestamp in the HELLO must be within 120 s of the host's clock (replay of an old HELLO is rejected; the joiner's nonce is also remembered for the session).
- **Limits (stated honestly):** a weak password can be guessed offline by someone who records a HELLO (the salt is in the code); the UI warns for passwords under 10 characters and offers a generated passphrase. There is no forward secrecy beyond the per-session nonces; a stolen password lets someone decrypt a recording of that session. Acceptable for a game lobby; documented.

## 4. Connectivity without a server

1. **UPnP IGD / NAT-PMP / PCP:** on Host start, request a UDP mapping for the port with a short lease, renewed while hosting and removed on exit. Preferred implementation: our own minimal NAT-PMP/PCP client (small) plus a UPnP IGD client; if a library is vendored it goes in CREDITS part 1 with licence. The result (mapped / refused / no gateway) is shown in the launcher, together with the external address.
2. **Manual forwarding:** guide in the launcher (and `docs`): router admin page, forward UDP 47474 to the host PC's LAN address; includes a "test" button that asks the host game whether the port is reachable (the joiner-side check is the real test).
3. **VPN (Tailscale / ZeroTier / WireGuard / Hamachi):** the code can contain the VPN address; nothing else to do.
- No relay and no STUN/matchmaking server. External address discovery: UPnP/NAT-PMP report it; otherwise the host types it or the launcher shows the local/VPN addresses; no third-party lookup service is called without the user's choice.
- Both players behind carrier-grade NAT with no VPN: cannot connect; the launcher says so and points to the VPN route. Hole-punching needs a rendezvous server and is out of scope.

## 5. Launcher <-> game interface

Settings the launcher needs (all optional; absent = online off, behaviour unchanged):

| Key (ini `[online]` in `ste_online.ini`, same name as env var with `STE_` prefix) | Meaning |
|---|---|
| `mode` = `off` / `host` / `join` | default `off` |
| `port` | UDP port to listen on (host) or the local source port (join); default 47474 |
| `code` | join: the host code |
| `password` | passed to the game by the launcher at start (env `STE_ONLINE_PASSWORD` in the child process, never written to disk by the game) |
| `players` | host: 2..4 |
| `upnp` = `auto` / `off` | host: try to open the port |
| `bind` | host: optional local address to listen on |

Status the game reports (a small JSON file `ste_online_status.json` in the data dir, rewritten on change; the launcher polls it): `state` (`starting`, `listening`, `mapped`, `connected`, `error`), `code` (host: the string to share), `external_address`, `mapping` (`upnp`/`natpmp`/`none`/`failed`), `peers` (count, slot, round-trip ms, packets lost), `error` (text). The launcher screens (see `NOTE_FOR_LAUNCHER_online_host_join.md`): Host (password, players, Start, shows code and mapping result, Copy button), Join (code, password, Join, progress and a plain-language failure reason: "no answer" covers wrong password, closed port and host offline, deliberately not distinguished).

## 6. Where we are, and the plan

Known so far (see `REPORT_BETA_NIC_TRACE.md`): the title's driver starts the NIC (rings, interrupts) about 1.6 s after boot, polls link through the kernel call `PhyGetLinkState`, and kicks TX/RX every 203 ms. With link forced up (`STE_ETHERNET_LINK=up`, now answering 100 Mbit full duplex) the game reaches Multi-player > System Link without crashing, but **no frame is queued for transmit**: only TX descriptor 0 gets a buffer pointer, never the owned flag. So the open problem is first "why does the XNet stack not transmit", not the tunnel.

Order of work, each step reported before the next:
1. **XNet start-up logging:** interrupt status register, `XNetStartup`/DHCP path, what the System Link screen calls; find what the stack waits for (an interrupt, an RX completion, an address). Logging only.
2. **Minimal NIC behaviour, only when online mode is on:** acknowledge interrupts, complete TX descriptors, accept RX. Default stays byte-identical.
3. **Loopback test:** two instances on one PC (separate save dirs), frames passed through a local socket without crypto, to prove System Link discovery works.
4. **Tunnel:** Monocypher handshake + AEAD, virtual switch on the host, rate limits; unit tests on the crypto framing (wrong password, replay, truncated, oversized).
5. **NAT mapping** (UPnP/NAT-PMP) and the manual-forwarding guide.
6. **Test:** two instances on test PC A, then test PC A vs test PC B on a home LAN (steps in `ONLINE_TEST_STEPS.md`), then over the internet with a VPN and with a forwarded port.
7. **Launcher screens** from the note; docs in `docs\formats` and the novice guide; credits check (Monocypher in part 1, anyone whose research helped in part 2).

Open questions: the MTU (Ethernet frame up to 1514 plus ~33 bytes of tunnel overhead exceeds a 1500-byte path MTU; the game's frames are small in practice, we will measure and either allow IP fragmentation or lower the guest MTU); host migration is not planned (host leaves = session ends).

Credits: our own code. Monocypher (when vendored) is listed in [CREDITS.md](../CREDITS.md) part 1; network-card behaviour is derived from our own traces, no code from xemu or any other emulator is used.
