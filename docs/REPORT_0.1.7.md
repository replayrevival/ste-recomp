## 4. Menu-clip audio + deterministic seed (c410)
- Cause of the silent menu WAV: the APU only writes samples while the game runs, so during the pause (and loads) the file does not advance; the wall-clock offset between video and WAV then points past the end of the file. Fix: RECOMP_AUDIO_WAV_WALL=1 (lib apu_wav.c) pads the file with silence whenever more than 200 ms of wall time is missing, so wav time == time since the first sample; clips.ps1 sets it and pads the end with apad. Opt-in; the default file format meaning is unchanged.
- Seed: STE_RAND_SEED=<n> (ste_textentry.c seed_frame) writes the CRT rand() seed word (guest 0x003F8984, LCG 214013/2531011 = sub_001A5317) on the frame the mode word 0x003562B4 becomes 4 (match start). Harness option, off by default. Determinism result: see below once measured.

## 4b. Deterministic seed: result (c414, STE_RAND_SEED=1234)
- The seed is applied ([SEED] f=17809 match start). Two recordings of the same pad script (1280x720, 20 s windows, seed_1/seed_2 in F:\GodzillaSTE_work\clips_smoke) share NO identical frame (md5 of every frame downscaled to 160x90, searched at every alignment): the takes differ from the first frame. So the seed alone does not make two takes equal: the fight simulation runs on the real frame time (delta-time driven, see memory gpu-vp-and-dt-timing), loading and start-up timing differ run to run, and effects/AI draw from more than the CRT rand(). A fully reproducible take would need a fixed simulation time step (not offered by the game; changing it would alter game logic, so not done). Consequence for the media: compare/draw-distance takes start from the same pad script and drift apart; to compare features use two settings in ONE take (e.g. toggle the overlay setting mid-fight) or accept the drift. STE_RAND_SEED stays as a harness option (e.g. to make AI/random choices repeat where timing allows).

## Draw-distance pop-in in the showcase clips (2026-11-19, c417)
Cause 1 (clips): `tests\clips.ps1` passed `-Scale 1` to perf_live, so every Unlimited clip ran with `STE_VIDEO_QUERY_SCALE=1` (log `[QVOL] query_scale=1`, far bound 1230 unwidened): the render-list query never returned the far buildings, which then popped in at about 1230 units. The governor was not involved (0 `[QGOV]` events in those logs). Fixed: clips.ps1 takes `-QScale` (default 4) and sets `STE_VIDEO_QUERY_AUTO=0` (a recording is not a benchmark).
Cause 2 (player): with the governor on at x4, 1080p, unrecorded (run F:\GodzillaSTE_work\gov_x4_auto, c416): 87 `[QGOV]` events, scale swinging 3.98 -> 1.85 -> 3.98 in the fight; fps median 58.9, windows < 50 fps: 4 of 89. Governor off (gov_x4_off): median 59.0, < 50 fps: 9 of 89. The governor bought little on this PC and visibly shrank the skyline. c417 adds a floor for the LOAD governor only (`query_scale_floor` / `STE_VIDEO_QUERY_FLOOR`, default 3.0; the pushbuffer-overrun guard may still go lower): run gov_x4_floor: scale 3.06..3.98, 63 events, fps median 59.05, < 50 fps: 5 of 89. Default query_scale is 1.5 (<3), so the load governor is inert at defaults.
Recording trap found: at x4 and 1080p the recorder load drops the game to about 35 fps (417 frames in a 12 s window), so the 60 fps clip plays ~1.7x fast even though check_clip says SMOOTH. clips_dd.ps1 now also requires frames >= 97 % of secs*60. That clip is kept aside as `draw_distance_unlimited_x4_REJECTED_fast`.
Far-skyline pop check: `tests\pop_check.py` (block frame-diff) is NOT a reliable discriminator on a moving scene (it flags breath beams and helicopters); inspection of flagged frames showed no building pops in the x4 take. Not claimed as proof.
Not done: hold/cross-fade of objects leaving the band, "never shrink while the camera is still". 0.1.6 Unlimited clips were recorded at x1 and should be re-recorded if used again.
