# Photo mode / free cam: design and findings (2026-11-20, report first, nothing built yet)

## 1. Spec (the maintainer)
v1 photo mode: in-game menu entry + optional hotkey; pauses the match like the overlay does; HUD toggle; free camera from the current view; pad (LS move, RS look, LT/RT down/up, LB/RB slow/fast, A screenshot, B exit) and keyboard/mouse (WASD + mouse, Q/E, Shift, F12, Esc); FOV, optional roll; exact camera restore; scene queries follow the camera; limited flying range; works with the overlay, fullscreen, 16:9/21:9, controller only. `[camera] photo_mode` setting. v2 live free cam: report first (section 4).

## 2. What exists
- **Debug free camera (c214, `tests\freecam_hook.inc`, `tests\make_freecam_cand.ps1`)**: debug-only, built from the c86 chunks with two hand-patched call sites: in `sub_001E9E60` (the fight camera manager) the view data `p` (12 floats, D3D view layout, camera axis basis + translation) is passed to `ste_freecam_view(p)` just before the call to `sub_0001FA30` (guest call at 0x001EA1D8), so the camera object, its frustum and everything derived from it follow the free camera; and the entry of `World_Update(dt)` `sub_00084800` returns at once while "frozen" (so the sim stops but the frame still renders). Keys F9/F10/F11, WASD/QE/arrows, scripted flights, screenshots (`g_ste_fc_shot_req`). Proven in earlier rounds (draw-distance and tint-flash work used it).
- **Overlay pause** (`ste_overlay_wait_if_paused()` in the frame hook of `ste_pb_hook.c`): holds the GAME THREAD at the end of the frame; the render thread keeps presenting the last frame. Game input is zeroed while the overlay is visible (`ste_sdlinput.c`). This pause shows a still image: it cannot move the camera, because nothing new is submitted.
- Backbuffer capture (`d3d8_capture_backbuffer_bmp_public`, used by STE_SHOT_DIR/ F12 screenshots) writes BMP; a PNG path for `<data>\screenshots\` is a small addition (stb/own deflate or Windows WIC).
- Query volume / draw distance machinery (query_scale, draw_distance overrides) is camera-relative; the debug cam showed far objects stay drawn when the overrides are on.

## 3. The decision needed (STOP rule: skipping game logic / generator change)
A photo mode that keeps rendering while the match is frozen needs the **simulation to be skipped but the frame submission to run**. Options:
| option | how | cost / risk |
|---|---|---|
| A (recommended) | extend the generator's hook feature (`docs\formats\RECOMP_HOOKS.md`, added c198) with a mode `return` = "if fn() returns non-zero, pop the arguments and return from the function" (generic, used for `World_Update` and nothing else), then add two hooks in `ste_hooks.toml` (camera call site 0x001EA1D8 `before`, World_Update entry 0x00084800 `return`) and regenerate the production chunks | generator change (needs approval), regeneration of chunks 0004 and 0012 (0012 is already a hand-patched chunk in the production lineage, so its patches must be re-applied: use the c372-style regeneration), a new candidate c433; exact freeze (no state change) |
| B | hook `before` at World_Update entry that sets `dt = 0` (no generator change) | the sim is not exactly frozen: game clock / round timer may keep running and AI RNG advances; division by zero in code that divides by dt unknown; fails the "no change to game state" requirement |
| C | pause the game thread (overlay style) and re-render the last frame with a patched view in the Kelvin layer | no game-logic change, but the render thread only replays pushbuffers: view-dependent constants are baked per draw, culling already happened; not viable for a free flight |
Also needed for any option: input mask (the game gets a released pad while photo mode is on, same as the overlay), HUD hide (skip the 2D HUD pass: needs a HUD draw marker, probably the Kelvin ortho pass flag; found in the tint-flash work), flying-range limit from the arena bounds, a PNG screenshot writer, the overlay menu entry ("Photo mode") and the `[camera]` ini keys, then the proof matrix (Tokyo + New York, 16:9 + 21:9, clean-resume check, controller only).
Effort: option A about 3-5 days (generator mode + regen + candidate + input + HUD + proof); photo mode without a freeze is not possible.

## 4. v2 live free cam (report)
A camera detached while the fight runs is the same camera hook with the sim running. Risks: (1) game camera logic keeps updating its own camera and several systems read it (target lock, off-screen indicators, hit-flash quad sizing, AI "spawn around the camera" for traffic/vehicles): they would see the free camera; (2) audio listener: if the APU listener is taken from the camera object, sound pans/attenuates around the free camera (could be wanted or not; needs a hook to pin it to the player); (3) culling/query volume follow the camera, so objects around the monsters can vanish when the camera flies far away (physics/AI of culled objects does not stop, but their visuals do); (4) control routing: the player must still control the monster while the camera is driven by other inputs (second stick/keyboard), so the photo-mode input mask cannot be reused as is; (5) save/soak risk is low (no state writes) but every camera-derived system is a regression surface. Recommendation: build v1, then enable the live mode only for a short list of arenas after a soak.

## 5. Status (2026-11-21): implemented in 0.3.1 (option A)
